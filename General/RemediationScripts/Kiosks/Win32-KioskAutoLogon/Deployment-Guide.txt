HOW REPAIR / DETECTION WORKS
The first deployment runs even if the old platform script already configured
auto-logon: it has no matching completion marker for this Win32 deployment.
The installer updates the existing account password and disables account/password
expiration, optionally removes DeviceLock keys, stores the password as an LSA
secret, and configures unlimited local auto-logon. It verifies the basic settings
before writing DeploymentVersion under:
HKLM\SOFTWARE\UMDLibraries\KioskAutoLogon

Detection requires the exact deployment version, the expected account, enabled
account with nonexpiring password and unexpired account, AutoAdminLogon = 1,
the expected username and local computer domain, no plaintext Winlogon password,
no AutoLogonCount limit, and a nonempty DefaultPassword LSA secret.
It exits 0 with output only when detected; otherwise it exits 1 silently.
Required Win32 apps can be offered again when Intune reevaluates them as missing.
This is eventual repair, not immediate monitoring or a guaranteed check interval.
It does not validate the secret against the actual account password, detect all
policy conflicts, or prove a successful reboot logon.

FORCE A FUTURE REPAIR EVEN IF DETECTION CURRENTLY PASSES
1. Increment DeploymentVersion in Source\KioskConfig.json, for example:
   2026.10.06.2
2. Change requiredVersion in Detect-KioskAutoLogon.ps1 to the same value.
   If changing the account, also update expectedUser in that detection script.
3. Rebuild the package with the command below.
4. Replace the app package AND uploaded detection script in Intune; retain the
   Required assignment. Old versions will fail the new version check and rerun.
Merely syncing or replacing content with the same version does not force a rerun
when detection still passes. For periodic policy repair consider Intune
Remediations as a separate option.

SECURITY AND POLICY NOTES
KioskPassword.txt contains the existing password as plaintext. A SecureString
conversion protects how the account cmdlet receives it, not the bundled file.
The .intunewin format is packaging, not a credential vault; administrators and
endpoint SYSTEM/admin access can recover credentials. This generated package
directory is restricted to SYSTEM, local Administrators, and the creating user.
Do not commit the credential/package to Git, attach it to tickets, or distribute
it broadly. Rotate the existing shared password through your approved process;
update the bundled file, increment the version, and rebuild for deployment.
The installer does not copy the password file into endpoint deployment logs.
Intune's own unpacked content/cache can still contain it.
Auto-logon grants physical users the kiosk account's access; keep it nonadmin.
LSA secrets are accessible to local administrators/SYSTEM.

RemoveDeviceLockPolicies is true to match the original working repair. Deleting
these keys can weaken lock protections. Scope strictly to kiosk devices and
correct conflicting policy assignments/exclusions in Intune; assigned policies
can reapply them. Set the flag to false and rebuild if cleanup is unnecessary.
Do not disable CrowdStrike/Rapid7. If password or LSA changes raise detections,
review with security staff and use narrowly scoped approved exceptions only.

UNINSTALL
Remove the Required assignment before assigning Uninstall. Uninstall disables
auto-logon, removes the LSA password and completion marker, and leaves the local
account/password and current session in place. It refuses to change a different
auto-logon username. It does not restore deleted policy keys or the prior password;
reapply desired DeviceLock settings through Intune.
